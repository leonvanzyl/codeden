# Security

CodeDen runs coding agents on your machine with your logins. Its security model keeps the local API private to you, keeps credentials out of files and transcripts, and puts risky agent actions in front of you before they happen.

To report a vulnerability, see [SECURITY.md](../SECURITY.md).

## Network

- By default the **server and the runner listen on 127.0.0.1 only.** Nothing is exposed to your LAN or the internet.
- **Network access is opt-in** (Settings › Network access, or `codeden network on`): it needs a password and then moves only the server's web listener to all interfaces on the same port, so phones and tablets on your network or VPN can sign in. The runner, its MCP proxy and the agents' `/mcp` endpoint stay on 127.0.0.1. See [Network access](#network-access) below and [Phones, tablets and network access](remote-access.md).
- **Every local request needs the install token**: a random 256-bit token in `~/.codeden/install-token`, created on first run (readable only by you where the OS supports file modes). It's required on every HTTP, WebSocket and MCP request, and compared in constant time.
- **The browser gets the token once**, through the launch URL that `codeden` opens. The server swaps it for an **HttpOnly, `SameSite=Strict` cookie** and redirects to a clean URL, so the token doesn't linger in your address bar or history. Opening CodeDen without it shows a "CodeDen is locked" page.
- **`Host` must be a loopback name** (`127.0.0.1`, `localhost`, `[::1]`), which blocks DNS-rebinding attacks.
- **`Origin`, when present, must be CodeDen's own**, which blocks other websites, including other apps on other localhost ports.
- The cookie name includes the port, so two installs side by side don't clash.

### Network access

Off by default. When you turn it on:

- **A password is required.** At least 15 characters; very common passwords, repeats and simple sequences are refused. Only a **salted scrypt hash** is stored (`~/.codeden/remote-access.json`, mode 0600 where supported). CodeDen refuses to bind beyond 127.0.0.1 without one, at startup too. Changing it signs out every remote device.
- **Remote means "not loopback"**, judged from the connection's peer address (`127.0.0.0/8`, `::1` and their IPv4-mapped forms are local). `X-Forwarded-*`, `Forwarded` and `X-Real-IP` are never read.
- **Remote devices sign in with the password** and get a random session token in an **HttpOnly, `SameSite=Lax` cookie** (`Secure` over HTTPS), valid for 90 days. Only its SHA-256 hash is stored, with the device's user agent and when it was last seen. **The install token is never accepted from a remote device**, in a header, a cookie or `?token=`.
- **Failed sign-ins are throttled per address:** after three, each attempt waits 1 s, 2 s, 4 s … up to 30 s; ten in 15 minutes lock the address out for 15 minutes. Only failures count, other devices are unaffected, and each failure is logged with its address (never the password) in `~/.codeden/logs/remote-access.log`.
- **Reachable remotely, behind the session:** the web UI, the HTTP API and the UI WebSockets. **Never reachable remotely:** `/mcp` (404), the runner and its MCP proxy (still 127.0.0.1), and changing network access or the password (403; this computer or the CLI only).
- **`Host`** may also be one of this computer's own LAN or VPN addresses on CodeDen's port while access is on, and **`Origin`** may be the matching `http://<address>:<port>`. Other hosts, other ports, foreign origins and `null` origins are refused.
- **Signed-in devices** are listed in Settings with **Sign out** and **Sign out all**; signing out (or turning access off) also closes their open connections.
- Network access serves plain **http**: use it on networks you trust, or over your own VPN (Tailscale, WireGuard). Never forward the port to the internet.

## Agents and MCP

- Each agent session gets its own **MCP token** for CodeDen's internal MCP server, minted when the session starts or resumes, **stored only as a SHA-256 hash**, and **revoked** when the session stops, completes or fails. The install token is not accepted on the MCP endpoint, and MCP tokens are not accepted by the UI API.
- Tokens are **role-scoped**: the orchestrator, PMs and agents see only the tools for their role; others aren't even listed. Browser tools always act on the caller's own session, and no tool takes another session's id.
- Agents reach CodeDen through a **local MCP proxy in the runner** on `127.0.0.1`. The token is passed to Codex over stdin, never on a command line.
- **Agent environments** inherit your environment minus CodeDen's own variables: no `CODEDEN_*` variable (CodeDen's data folder, its installer, its secrets) reaches agents, terminals or setup scripts, so an agent can't find CodeDen's home through its environment and a CodeDen checkout's tests run against their own stubs. (Your other environment variables are passed through, as they would be in your own terminal.) Agent sessions also get **`CI=true`**, so no command waits on a prompt nobody can answer; your tools then behave as in CI. You can turn it off per project; see [Troubleshooting](troubleshooting.md#tests-installs-or-builds-behave-differently-in-agent-sessions).
- Tokens are never logged or written into transcripts.

## The orchestrator and PMs can't write code

They always run read-only, whatever their level: Claude gets no edit tools and a policy that denies writing commands (checks included), Codex runs in a read-only sandbox, and OpenCode's, Cursor's and Gemini CLI's edits and writing commands are refused by CodeDen's policy (Cursor also runs in its read-only `ask` mode). They act only through CodeDen's tools.

## Permissions

Each agent session and each automation runs at a **permission level**, from Read-only to Full. The default comes from **Settings → Autonomy**; change it per session in the composer's **Permissions** picker (in a new session too, before its first message), and per automation in its editor. Each level maps onto the provider's **native** enforcement:

| Level | Claude Code | Codex | OpenCode |
|---|---|---|---|
| **Read-only**: can read and run checks, but never edits files, commits or pushes | Default permission mode; a PreToolUse hook denies the edit tools and every shell command that is not on the read-only allowlist | `never` approvals, **read-only sandbox**, network off: writes fail instead of asking | Every edit is refused, and every command not on the read-only allowlist |
| **Supervised**: asks before edits and commands | Default permission mode, and every edit or command is routed to an approval | `untrusted` approvals, workspace-write sandbox | Every edit and command is routed to an approval |
| **Auto**: works freely in its worktree and asks only for risky actions (default) | `acceptEdits`, plus CodeDen's risk classifier on every tool call | `on-request` approvals, workspace-write sandbox, network off; what Codex asks to run outside its sandbox goes through CodeDen's risk classifier, and only risky actions reach you | CodeDen's risk classifier on every edit, command, outside path and fetch; only risky actions reach you |
| **Full**: never asks | `bypassPermissions`; only writes outside the worktree, CodeDen's own credential files and [agents' own allow-lists](#agents-own-allow-lists) ask | `on-request` approvals, workspace-write sandbox, network on; CodeDen approves Codex's requests unless they write outside the worktree, touch CodeDen's own credential files or write an agent's allow-list | Only writes outside the worktree, CodeDen's own credential files and agents' own allow-lists ask |

**How Codex's requests are decided.** Codex's workspace-write sandbox keeps `.git` read-only, and under Auto it keeps the network off, so Codex asks to step outside it for ordinary work such as `git commit`, `pnpm install` or `git push`. Under Auto and Full, CodeDen judges each request with the same risk classifier as Claude's tool calls: commands by their text, patches and extra folder permissions by their paths. What your level allows is approved at once and shows in the transcript as approved by policy; only the rest becomes an approval card. A command approved this way runs outside Codex's sandbox, just as Claude's commands run outside any sandbox. Under Supervised and Read-only nothing is approved by policy.

OpenCode has no OS sandbox of its own. CodeDen gives its sessions permission rules that make every edit, command, path outside the worktree and web fetch ask, and answers each request with its own policy, the same classifier Claude uses: approved on the spot, refused with a reason, or shown to you. **Approve for session** is kept by CodeDen for that session only: OpenCode's own "always" would save the rule for every session in the repository, so CodeDen never sends it. The OpenCode server CodeDen starts listens on `127.0.0.1` with a random password, and a small plugin removes that password (and the config carrying CodeDen's MCP token) from the environment of the agent's shell commands.

Cursor's CLI asks before the tool calls its own rules gate, over its ACP server (`agent acp`), and CodeDen decides each request by level exactly as for OpenCode, with the same classifier. CodeDen never starts it with `--force`, and only ever answers "once": Cursor's "always" option would save the rule in your Cursor settings. Known gap: what Cursor's own allowlist (`~/.cursor/cli-config.json`, a project's `.cursor/cli.json`) allows runs without asking, so CodeDen only sees what Cursor asks about. Cursor has no option to ignore a project's allowlist, so CodeDen guards the file instead (below).

Gemini CLI works the same way over its ACP server (`gemini --acp`). CodeDen runs it in its `default` mode, which asks before every edit, command and MCP tool, switches a session that opens in your `yolo` or `autoEdit` default back to it, and never passes `--yolo` or `--approval-mode`. Gemini CLI names the MCP server of each tool it asks about, which is how CodeDen recognises its own tools; a command or an edit is judged as one whatever it is called. CodeDen also starts it with an **admin policy** (`--admin-policy`, the file `gemini/admin-policy.toml` in CodeDen's data folder). Admin rules outrank everything Gemini CLI's settings and your own policy files allow (`tools.allowed`, MCP servers marked `trust` or listed in `mcp.allowed`), so commands always ask, and edits and MCP tools ask outside plan mode, and CodeDen decides each one. Known gap: other tools those settings allow (web fetches, for example) still run without asking, and so do edits and MCP tools they allow while Gemini CLI plans, where its own plan rules decide. Gemini CLI ignores `--admin-policy` when your machine has system policies of its own.

**Trade-off: your own Gemini CLI deny rules no longer apply in CodeDen sessions.** Admin rules outrank what you *deny* in Gemini CLI too: a `deny` rule in your or the project's policy files, a `tools.exclude` entry, or an excluded MCP server, for commands, edits or MCP tools (edits and MCP tools outside plan mode). Gemini CLI then asks instead, and CodeDen's permission level decides. At Auto, CodeDen's classifier asks you about risky commands such as force pushes. At Full it allows them, so a Gemini CLI rule that denies `git push --force` won't stop it in a CodeDen session. Use Supervised, or a lower level, for work where you relied on those rules.

### Agents' own allow-lists

An agent could switch CodeDen's approvals off by writing its own allow-list. A single step like `echo '{"permissions":{"allow":["Shell(*)"]}}' > .cursor/cli.json` would do it, and once merged it would apply to every later Cursor session in the project. So creating or changing one of these files asks at **every** level, Full included, in every edit and command CodeDen judges (Claude Code's, OpenCode's, Cursor's and Gemini CLI's, and what Codex asks to run outside its sandbox):

- Cursor: `.cursor/cli.json`, and `cli-config.json` in `.cursor` (your `~/.cursor`) or a `cursor` config folder.
- Gemini CLI: `settings.json` and `trustedFolders.json` in `.gemini` (the project's or your `~/.gemini`), the system `settings.json` and `system-defaults.json` in `gemini-cli`, and any policy file in `.gemini/policies` or `gemini-cli/policies`.
- Copying or moving something into a `.cursor` or `.gemini` folder.

This covers the agent's edit tools and shell writes: redirects (`>`, `>>`), `tee`, `cp`, `mv`, `ln`, `dd of=`, `sed -i`, `git checkout`/`restore`/`mv`, PowerShell's `Set-Content`, `Out-File`, `Copy-Item`, `New-Item` and `[IO.File]` calls, and inline code (`node -e`, `python -c`) that names one. Reading, searching, diffing, staging or deleting them doesn't ask.

Known gaps:
- **Codex** edits files and runs commands inside its workspace-write sandbox without asking, at Auto and Full. Those writes never reach CodeDen, so a Codex session can write one of these files in its worktree; only what Codex asks to run outside its sandbox is judged.
- **Paths CodeDen can't read from the command**, such as one built while it runs (`> $f`), or a program that writes the file itself.

That's why CodeDen also checks at the start of each session. When a Cursor or Gemini CLI session starts in a worktree that already has rules like these (`permissions.allow` in `.cursor/cli.json`; `tools.allowed`, `tools.autoAccept`, `mcp.allowed` or a trusted MCP server in `.gemini/settings.json`; `allow` rules in `.gemini/policies/*.toml`), its first turn shows a warning naming them. For a factory session, the warning also goes on the factory item and into your inbox, since nobody may be watching the transcript. Check such rules before relying on CodeDen's levels: they may have come in with a merged change.

Read-only is offered only on providers that report the `readOnly` capability (Claude Code, Codex, OpenCode, Cursor and Gemini CLI all do); the server refuses it elsewhere. Under Read-only:

- **Claude** may run commands that only read (`ls`, `cat`, `rg`, `cd`, `sed` scripts that only print such as `sed -n 1,40p`, `git status`/`log`/`diff`/`show`/`stash list` including `git -C <dir> …`, `gh ... view`/`list`/`checks`, `gh search`, `gh api` GET requests, and their PowerShell equivalents) and the project's **checks**: `npm`/`pnpm`/`yarn`/`bun` `test`, `lint`, `typecheck` or `check`, `tsc`, `vitest`, `jest`, `eslint`, `biome check`, `ruff check`, `pytest`, `mypy`, `cargo test`/`check`/`clippy` and `go test`/`vet`. Fix, write, snapshot-update and watch flags (`--fix`, `--write`, `-u`, `--watch`, ...), output redirection and command substitution are refused, and so are the options that make a reading program write or run something (`sort -o`, Windows `sort /O[UTPUT]` and `/T[EMPORARY]`, `uniq` with an output file, `find -fprint`/`-exec`, also after `--`, `fd -x`, `rg --pre`, `less -o`, `tree -o`, `date -s`, `git diff --output`, `git grep -O`, `git ls-remote --upload-pack`), git's writing forms (creating a branch or tag by name, `git remote`/`worktree`/`reflog` changes, `git config` writes, abbreviations included), `gh` verbs other than view, list, status, diff and checks (and `gh` extensions), unquoted parentheses and braces (PowerShell runs code in them, even after an allowed cmdlet), background jobs (`&`), installs, builds, commits and pushes. Options are read from the words the shell actually passes (`-'o'` is `-o`); variable expansion, `$'…'` quoting and unquoted patterns that could expand to an option are refused, since what they pass can't be read from the command. Checks run the project's own scripts, so a test that writes files (coverage, caches) can still write them; the agent itself cannot.
- **Codex** runs every command in its read-only sandbox, so checks run but any write fails.
- **OpenCode** follows the same allowlist as Claude: commands that only read and the project's checks run; edits and every other command are refused with the reason, which the agent sees.
- **Cursor** runs in its read-only `ask` mode, and CodeDen's policy refuses edits and commands outside the same allowlist.
- **Gemini CLI** stays in its `default` mode, which asks before every edit and command, and CodeDen's policy refuses edits and commands outside the same allowlist.
- **CodeDen's `create_pull_request`** is hidden from read-only sessions and refused if called. Commenting on issues and attaching screenshots as evidence still work, so the agent can report what it found.

Changing the level while a session runs is saved on the session and sent to the running agent. Claude, OpenCode, Cursor and Gemini CLI follow it from their next tool call, into and out of Read-only too; Codex from its next turn (the composer tells you which). Approvals that are already waiting stay waiting.

### Plan mode

**Plan** in the composer (in a new session too, before its first message) has the agent plan before it builds. While it plans, CodeDen refuses file edits and writing commands at **every** level, Full included, with the same command rules as Read-only: the agent can read, search and run the project's checks, and write only its own plan notes (Claude's plans folder), at Read-only too (under Supervised that write still asks). Claude Code's own plan mode would otherwise send edits to CodeDen's approval policy, which Auto and Full approve, so CodeDen enforces it itself. The plan ends in a **Plan ready** card: approving lets the agent implement at the session's permission level, and **Keep planning** sends your note back so it revises the plan. Turning Plan off without approving returns the session to its permission level straight away.

Cursor and Gemini CLI plan in their own `plan` modes, with the same refusals from CodeDen. Gemini CLI's plan ends when it asks to leave plan mode (`exit_plan_mode`): CodeDen shows its plan file and the **Plan ready** card. Gemini CLI can't take a note with **Keep planning**, so send what to change as your next message. While planning, any other tool Gemini CLI asks about that CodeDen can't identify goes to you at every level.

## Automations

Automations run unattended, so they use the same permission levels with safer defaults around them: new, imported and PM-created automations always start **off**, an import never runs anything and warns about Full permissions, and imports are parsed with the same validation as automation files, within limits on file count and size. See [Automations](automations.md#sharing-export-and-import).

**The OS temp directory counts as part of the workspace** under Auto and Full: writing or deleting files in `os.tmpdir()`, `%TEMP%`/`%TMP%`, `$TMPDIR` or `/tmp` (including Git Bash's `/tmp` on Windows) doesn't ask, and Codex's sandbox may write there. Only the temp directories themselves qualify, never a filesystem root or your home directory, even if an environment variable points there. Secrets files written to temp still ask, and Supervised still asks for everything.

**Claude's own notes count the same way.** For Claude sessions under Auto and Full, writing plan files (plan mode, `~/.claude/plans` or your `plansDirectory`) and the project's auto-memory (`~/.claude/projects/<project>/memory` or your `autoMemoryDirectory`) doesn't ask. Only your own Claude settings can move these folders (a repository's settings can't), and a folder that would cover Claude's config folder (its settings and credentials), your home directory or a filesystem root is ignored. Claude's settings and credentials, and secrets files, still ask.

Under **Auto**, edits and ordinary commands inside the worktree run freely, and these go to an approval card (and your inbox):

- writes or deletes **outside the worktree** (and outside the OS temp directory), and changes to global git config (reading it, such as `git config --global user.email`, doesn't ask);
- **force pushes**, deleting branches with unmerged work (`git branch -D`), tags or refs, and deleting remote branches. A force push **with a lease** of the session's own branch (`git push --force-with-lease` after a rebase, to the branch of its own worktree) doesn't ask: the lease refuses if someone else pushed there since, and it never applies to the base branch or `main`/`master`. `git branch -d`, which refuses to delete unmerged work, doesn't ask either. `create_pull_request` pushes the session's own branch with a lease when a plain push is rejected after a rebase;
- **global installs** (`npm -g`, `pip` outside a project, system package managers) and elevated commands (`sudo`);
- **piping a downloaded script into a shell** or executing a download (`curl … | sh`, `irm … | iex`, `curl … | python3`). Piping a download into a program that only reads it as data, such as `node -e '…'`, `python -c '…'`, `jq` or a script file in the project, runs freely;
- **secrets access**: reading secrets files (`.env`, `.npmrc`, SSH keys, `*.pem`, ...) and dumping the environment. Searching for a pattern such as `process.env`, mentioning a file name (`echo .env >> .gitignore`), checking that one exists, listing them, and creating or editing one inside the worktree (`cp .env.example .env`) are not reads and run freely. Printing a named variable such as `printenv PATH` doesn't ask either, unless its name looks like a credential. Writing a secrets file outside the worktree, temp included, asks as a write outside the worktree, under Full too;
- network fetches to hosts not on the allowed list, where a list applies.

When you approve, you can approve once or for the rest of the session.

**CodeDen's own credential files always ask.** The install token (`~/.codeden/install-token`), the runner's lock file with the runner's token (`~/.codeden/runner/runner.json`) and the network access store (`~/.codeden/remote-access.json`) would let an agent drive CodeDen itself and approve its own requests. So reading, writing or deleting one, copying or searching the folders that hold them (or a folder above them, recursively, unless the search's name filters leave them out), listing them by name, or a wildcard that matches them asks at **every** level, Full included, and is refused for Read-only sessions, the orchestrator and PMs. This holds anywhere in a command, after an ordinary risky step too. The path may be written out, start with `~` or use `$CODEDEN_HOME` (`$env:CODEDEN_HOME`, `%CODEDEN_HOME%`). Files with the same names elsewhere, such as in your project, are unaffected. **Approve for session** covers these files only for the exact call you approved, in the same directory; approving Claude's whole Read tool doesn't cover them. Two limits remain:

- **Codex** runs commands it considers safe, such as `cat`, inside its own sandbox without asking, so CodeDen sees only what Codex asks to run outside it. Codex's sandbox doesn't stop it reading these files.
- **The classifier reads command words.** It follows paths, wildcards, `$CODEDEN_HOME`, recursive searches from a folder above the home (`rg -g install-token . ~`), search options however they're written (`grep -ne. file`, `grep -fFILE file`, `--`), each path in a PowerShell list (`Get-Content a,b`), and file lists handed on (`find ~ -name install-token | xargs cat`, `cat $(find …)`). The home's own path always counts as plain text, so a data folder named like `CodeDen [dev]` is guarded too. It doesn't catch a program that opens the file itself (a script, `node -e …`), or one that gets the path from somewhere the command doesn't show (a here-document, a file of names, a variable holding the whole path).

**Approvals nobody is there to answer are denied, never approved.** In a Dark factory project, the PM's and the factory's approvals are denied at once, with guidance to find a way that needs no approval or to flag it for you. Sessions started by an automation, a PM or the factory in other modes wait 30 minutes for you, then are denied the same way, so unattended work finishes instead of waiting forever. Sessions you start yourself wait for you. These denials are recorded as decided by CodeDen's policy.

## Credentials

- **Provider logins** (Claude Code, Codex, OpenCode, Cursor, Gemini CLI) stay with their CLIs. CodeDen runs your installed `claude`, `codex`, `opencode`, `agent` and `gemini`, which use their own logins and credentials; it never implements a login and never sees your password. For Gemini CLI, setup reads the login method from its settings, the Google account's email from `google_accounts.json`, whether its OAuth file exists (never its contents) and which login variables are set (never their values). CodeDen never calls Gemini CLI's `authenticate`, which would rewrite your chosen method and could clear a cached login.
- **GitHub** is read from `gh auth token` at runtime and kept in memory only.
- **Optional API keys** (ElevenLabs, OpenAI, Gemini, a fallback GitHub token) go into the **OS keychain** (Windows Credential Manager, macOS Keychain, Secret Service on Linux) through `@napi-rs/keyring`. They're never written to files or returned by the API, and cloud voice keys never reach the browser. If no keychain is usable, keys are kept in memory for the current run only.
- `settings.json` and `usage-settings.json` hold no secrets.

## Files

- Agents work in their own **worktrees** under `~/.codeden/wt/`. Checkpoints use hidden refs and a temporary index, so your branch and index are untouched.
- The **agent-config editors** can only reach known agent-config locations; `.git`, credential files and `..` paths are refused, and every overwrite is backed up first.
- **Image generation** writes only inside the session's worktree (never `.git`, never through a symlink that escapes).
- **Evidence and shared files never carry secrets.** `attach_evidence` publishes files to GitHub (public on a public repository, and kept in its history), and `share_to_chat` stores files as artifacts that `attach_evidence` can publish by id. Both refuse secrets files (`.env`, `.npmrc`, SSH keys, `*.pem`, ...; `.env.example` and the like are fine) and CodeDen's own credential files, at every permission level, wherever the file is. The check covers the path asked for, the real file behind any symlink, junction or aliased folder (artifacts attached by id included), the name it would be published or saved under, and an artifact's original name, also when a file symlink leads to an artifact's stored file. Every name is also checked as evidence publishes it: published names keep only letters, digits, `.`, `_` and `-` (anything else, path separators included, becomes `-`) and drop leading dashes and dots, so `-id_rsa`, `notes.p!em`, `credentials.js!on` and `service/account.json` are refused like `id_rsa`, `notes.pem`, `credentials.json` and `service-account.json`. The final names are checked too, after `-2`, `-3`, ... tell repeated names apart. Calls to CodeDen's own tools don't go through the approval flow, so these tools refuse instead of asking.
- The **browser** refuses `chrome://`, `edge://`, `devtools://` and `javascript:` URLs, and each session has its own browser context.

## What CodeDen trusts from GitHub

On a public repository anyone can open an issue, comment or review a pull request, and whatever reaches an agent is a prompt. So CodeDen decides by author before GitHub text starts or steers any work. Labels never count as trust, because issue templates can apply them for anyone.

- **Factory intake.** The software factory and the dark factory take on issues only from **trusted authors**: the GitHub account CodeDen uses (the one `gh` is signed in as) and the logins in the project's **Trusted authors**. Everyone else's issues are ignored, with no model call, session or comment, until you let one in, and work let in that way is never merged automatically. See [Who the factory works for](software-factory.md#who-the-factory-works-for).
- **Issue triage.** Even with `autoStart` on, triage starts a session by itself only for issues by the account CodeDen uses, the project's trusted authors, or people with write access to the repository (its owner, organization members and collaborators). Anyone else's ready issue, and one whose author GitHub can't check at that moment, becomes a "Should I take this on?" decision in your inbox. See [Who triage starts work for](automations.md#who-triage-starts-work-for).
- **Pull request feedback.** A review that requests changes is passed on to the session that owns the pull request only when the reviewer has write access, is the account CodeDen uses, or is one of the project's trusted authors. Anyone else's review reaches the project manager without its text and doesn't wake it. See [Feedback on your sessions' pull requests](github.md#feedback-on-your-sessions-pull-requests).
- **Issue and comment text is data.** The briefs CodeDen gives agents that read GitHub text (factory builders, reviewers and the scout, the PM triaging an issue and the session that resolves it) say that the issue text and its comments are input data, not instructions, and a session told about a review is told the same of comments and reviews from people without write access. The agent acts on the work they describe and ignores anything in them that asks it to reveal secrets or credentials, change CI, release or deploy files, contact unknown hosts or act outside the repository.

## Automatic merges

Automatic merging only exists in the experimental Software factory and Dark factory modes, and only when you turn **auto-merge** on: then behind merge checks, protected areas and server-enforced limits, with a kill switch. On a public repository anyone can open an issue, so the factory only takes on issues by **trusted authors** (the account CodeDen uses on GitHub and the logins you list); everyone else's are ignored until you let one in, and work let in that way is never merged automatically. See [What CodeDen trusts from GitHub](#what-codeden-trusts-from-github) and [The software factory and the dark factory](software-factory.md).

## Data and telemetry

Everything stays in `~/.codeden/` on your machine. CodeDen has no accounts and no hosted backend, and sends no telemetry. The only outbound traffic is your agents talking to their providers, GitHub through your `gh` login, the optional image and voice engines you turn on, and, unless you set **Updates** to *Off* in Settings > General, a request on start and every 6 hours to the npm registry for the latest `codeden` version (nothing about you or your projects is sent). Installing an update downloads that version from npm, and **What's new** fetches its release notes from GitHub when you open it.
